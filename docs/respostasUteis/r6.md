## 1. O que o FPMax realmente é

FPMax (Grahne & Zhu, 2005) é um algoritmo de mineração de itemsets: dado um conjunto de **transações** (linhas) e **itens** (colunas), ele encontra os **itemsets maximais frequentes** — conjuntos de itens que aparecem juntos em pelo menos `min_support` das transações, e que não são subconjunto de nenhum outro conjunto frequente maior. A contribuição algorítmica do FPMax é *não* enumerar o reticulado inteiro de itemsets: ele constrói uma FP-tree e poda ramos inteiros por superconjunto, o que importa quando há **muitas transações e/ou muitos itens**.

No domínio do PhyloTreeMiner, a codificação (do artigo fundacional, `docs/literatura/02-fpmax-mineracao-subarvores-frequentes.md`) é: cada **pipeline** (alinhador × método de inferência) é uma transação; cada **clado/subárvore** é um item; o suporte de um clado é a fração de pipelines que o contêm.

## 2. O que o código faz hoje

`BioComp_UFF/workflow/stability/stability.py:449-517` (`closed_patterns` + `maximal_patterns`) não roda FPMax. Faz isto:

```python
def closed_patterns(self) -> List[Pattern]:
    pipelines = list(self.clade_sets)
    total = len(pipelines)
    seen: Dict[FrozenSet[FrozenSet[str]], Pattern] = {}

    for size in range(1, total + 1):
        for subset in itertools.combinations(pipelines, size):
            common: Set[FrozenSet[str]] = set.intersection(
                *(self.clade_sets[name] for name in subset)
            )
            if not common:
                continue
            key = frozenset(common)
            if key in seen:
                continue
            carriers = frozenset(
                name for name in pipelines if common <= self.clade_sets[name]
            )
            seen[key] = Pattern(
                clades=tuple(sorted(common, key=lambda t: (-len(t), sorted(t)))),
                pipelines=carriers,
                support=len(carriers) / total,
            )

    patterns = list(seen.values())
    patterns.sort(key=lambda p: (-p.support, -p.size))
    return patterns

def maximal_patterns(self, min_support: float = 0.5) -> List[Pattern]:
    frequent = [p for p in self.closed_patterns() if p.support >= min_support - 1e-9]
    maximal: List[Pattern] = []

    for candidate in frequent:
        clades = set(candidate.clades)
        if any(clades < set(other.clades) for other in frequent):
            continue
        maximal.append(candidate)

    return maximal
```

Ou seja: para **cada subconjunto possível de pipelines** (não de clados), calcula a interseção dos clados desse subconjunto. Isso é `2^M` subconjuntos — com `M` (número de pipelines) tipicamente entre 4 e 10, no máximo `2^10 = 1024` interseções de conjunto. Depois, `maximal_patterns` filtra os que não estão contidos em nenhum outro (linhas 511-515) — o mesmo critério de "maximal" do FPMax. O próprio docstring do módulo já documenta essa escolha desde antes desta pergunta:

> "Como o número de pipelines M é pequeno (tipicamente 8 a 10), o reticulado de conjuntos de clados fechados pode ser enumerado exatamente em `O(2**M * |C|)`, dispensando heurísticas de mineração. `StabilityAnalyzer.maximal_patterns` devolve, portanto, os conjuntos maximais exatos — não uma aproximação." (`stability.py:9-13`)

## 3. São a mesma coisa, ou não?

A resposta tem duas camadas.

**Camada 1 — o resultado é idêntico.** Isto não é opinião do projeto: é uma propriedade formal de **análise de conceitos formais** (dualidade de Galois entre itemsets e conjuntos de transações). Num contexto binário item×transação, os itemsets *fechados* correspondem exatamente às interseções sobre subconjuntos de transações — é uma dualidade matemática, não uma coincidência. Iterar sobre `2^M` subconjuntos de **pipelines** (o que o código faz) e iterar sobre subconjuntos de **itens/clados** com poda de FP-tree (o que o FPMax faz) chegam ao **mesmo conjunto de padrões maximais**, no ponto `min_support = 0`. `docs/science/03-metricas.md §4.2` já registra isso formalmente, e é consistente com o que o oráculo independente do projeto confirma nos números reais.

**Camada 2 — o caminho para chegar lá é diferente, e a escolha não é arbitrária.** O código explora a assimetria do domínio: aqui há **poucas transações** (4 a 10 pipelines) e **muitos itens** (centenas de clados possíveis, para árvores de 49+ táxons). O FPMax foi desenhado para o caso oposto — **muitas transações**, poucos itens frequentes — que é o regime típico de mineração de mercado (milhões de compras, poucos produtos populares). Nesse caso oposto, enumerar `2^M` transações seria inviável, e a poda por FP-tree é indispensável. Aqui é o contrário: `2^M` com `M ≤ 10` é trivial (≤1024 interseções), e seria **mais caro**, não mais barato, montar uma FP-tree sobre centenas de itens só para encontrar o mesmo resultado que uma força bruta de 1024 passos já dá em milissegundos.

## 4. Não é o algoritmo, é falta de otimização, ou é uma decisão correta?

Nenhuma das duas do jeito que a pergunta original enquadra. É uma terceira coisa:

1. **Não é o algoritmo FPMax literal** — isso é fato, não há como contornar. O código nunca constrói uma FP-tree nem executa o procedimento de Grahne & Zhu.
2. **Não é "usar de forma errada" nem "não otimizada"** — na escala atual (`M ≤ 10`), é o oposto: rodar FPMax de verdade aqui seria *over-engineering*, trocando uma solução exata e mais simples de auditar por uma mais complexa que resolveria exatamente o mesmo problema, mais devagar relativamente (a poda de FP-tree tem *overhead* que só compensa quando `M` é grande).
3. **É uma substituição algorítmica formalmente equivalente, escolhida corretamente para a assimetria do problema em `M` pequeno** — documentada no próprio docstring do módulo desde antes desta pergunta, não um desvio silencioso.

## 5. Onde isso deixa de valer

A equivalência depende de `M` continuar pequeno. Se `M` crescer para a casa das centenas — é exatamente o que o **E7** da agenda de pesquisa ([`docs/science/04-agenda-de-pesquisa.md`](../science/04-agenda-de-pesquisa.md#e7--◐--onde-o-fpmax-passa-a-ser-necessário)) já propõe testar deliberadamente, ampliando o produto cartesiano de alinhadores × inferências × modelos × sementes — `2^M` deixa de ser trivial (`2^100` é impossível) e a poda de FP-tree passa a ser não só justificável, mas necessária. **Esse é o experimento que ainda não foi rodado**: hoje ninguém mediu o ponto de cruzamento onde a enumeração exata para de compensar e o FPMax de verdade passa a valer a pena. Até esse experimento rodar, a afirmação "o FPMax não é necessário nesta escala" é bem fundamentada, mas não é uma prova — é uma inferência a partir de `2^10` ser pequeno, ainda não de uma medição da curva de custo real do FPMax nesse regime.

## 6. Resposta direta

Não, não estamos rodando o algoritmo FPMax propriamente dito — estamos calculando o mesmo objeto matemático por um caminho diferente. E sim, essa escolha é a forma correta e mais eficiente **para o tamanho de `M` que o projeto usa hoje** — não é uma pendência de otimização, é uma decisão de engenharia que só precisaria ser revisitada se `M` crescer, o que é justamente o que o E7 (ainda pendente) mediria.
